25 ideas from Anthropic's prompting playbook

This is a breakout session from Code with Claude London, held on 19 May 2026. Margot van Laar, an applied AI engineer at Anthropic, works through two cases.

First, she rescues a support-bot prompt that broke after a model migration. Then she builds a scheduling agent from scratch.

Her thesis: let evals drive every change. Fix the whole system (prompt, model and harness) instead of adding louder instructions.

Evals first 1–4

1

Build evals before you touch the prompt.

Evals tell you whether a change actually helped. They also tell you whether the model can do the job at all.

Details · quotes · next step · diagram · timestamp

Evals tell behavior problems apart from capability problems

Watch at 2:53

A migration can break for two reasons. The new model may be capable but behave differently. Or it may simply be less capable.

Prompting fixes only one of them. A behavior change responds to prompt tuning. A capability gap doesn't, and no rewrite will close it.

Evals are the referee. They show you which case you're in before you spend hours rewriting.

"We need evaluations to provide that rigor to understand whether a change to our prompt is actually correlating to an improvement in its performance."

— Margot van Laar

"The second case is where actually the model that we're changing to isn't as capable and no amount of prompting is going to fix that."

— Margot van Laar
What to do with this

Before your next model migration, run your current eval set on both models and compare the results.

2

Cover controls, edge cases and limits.

Even a small eval set can be representative. It just needs all three kinds of case.

Details · table · quote · next step · timestamp

Three kinds of test case, even in a tiny suite

Watch at 4:09

Control cases. These are easy, clear-cut questions that should always pass. They catch breakage in the basics.

Edge cases. These are places where the model has failed before. The prompt has instructions to stop those failures, and the eval checks that the instructions still work.

Limits. These test whether the model knows its boundaries: when to hand off to a human, when to refuse, and when to share what it knows.

Her demo bot was a support agent for a fictional telco, Meridian Mobile. Its suite had five cases:

Test caseTypeWhat it checks
Data limit on the basic planControlA simple fact lookup
Next bill after a mid-month upgradeEdgeProrated billing math
Prepaid policy questionEdgeAnswers match written policy
Billing errorLimitEscalates to a human
Hotspot data on a legacy planLimitShares information it has

"where it should be handing off to a human or where actually maybe it should be point blank refusing to answer a request."

— Margot van Laar
What to do with this

Tag every case in your suite as control, edge or limit. Then fill any bucket that's empty.

3

Grade hard rules with code, not an LLM judge.

When a rule can be checked objectively, a function is cheaper and more reliable. Keep LLM judges for fuzzier answers.

Details · quote · next step · timestamp

If a rule can be counted, count it

Watch at 24:50

The talk used two grading styles. An LLM judge graded the support bot. A Python function graded the scheduling agent.

Code wins for hard rules. The scheduler had strict constraints. A function counts violations exactly, on every run, at no token cost.

Report counts, not just pass or fail. The demo showed the number of violations in each trial. That made progress visible even while every case still failed.

"we can actually use a just a Python function which programmatically checks for every schedule that's generated how many violations were made."

— Margot van Laar
What to do with this

List the rules in your task that can be checked objectively. Write a checker for those first.

4

Don't chase a single noisy regression.

Results vary from run to run. One drop after a good change may be noise, not a real problem.

Details · quote · next step · timestamp

Expect variance and judge trends

Watch at 10:32

What happened. After the cleanup, the prepaid case improved but the hotspot case had a regression. She noted it and moved on.

Why that was right. LLM outputs vary between runs. If you react to every blip, you end up chasing ghosts.

Come back with a targeted fix. She fixed the hotspot case later, on purpose, by finding its actual cause (idea 11).

"There's going to be some natural level of variance in the different runs of the eval and we'll come back to that case specifically to see if we can make the prompt consistently better in that area."

— Margot van Laar
What to do with this

Run each case several times. The scheduling demo used five trials per case.

7

Separate role, guidelines, policy, tone and data.

Use XML tags so each kind of content has its own place. If you can't tell them apart, the model can't either.

Details · quote · next step · diagram · timestamp

Watch at 9:15

Before. The instructions sat in one big paragraph. Reasoning steps, the role and "critical" rules were all mixed together.

After. XML tags marked off the role, the general guidelines, the policy, the tone of voice and the data. The customer's account details and message came last.

9

Enforce the format in the harness, not just the prompt.

API settings can guarantee what a prompt can only request. Use stop sequences and structured outputs.

Let the API do the enforcing

Stop sequence. She added a stop sequence for the closing XML tag. Generation stops there, so nothing trails after the answer.

Structured outputs. For complex schemas, structured outputs enforce the shape in code.

Debugging failure modes 10–17

10

Fix one failure mode at a time.

Isolate a failing case, find its cause, fix it and re-run. Then move to the next one.

Details · steps · quote · next step · diagram · timestamp

A repeatable loop for debugging a prompt

Watch at 13:21
  1. Run the eval.
  2. Pick one failing case.
  3. Read the model's output to see what it actually did.
  4. Find the line in the prompt it's following, or the capability it lacks.
  5. Change that one thing, re-run, and confirm the fix.

Every fix in the talk followed this loop. She traced the hotspot, proration and billing failures to one line or one missing capability each.

Avoid long ban lists. Her recap lists this among the moves that helped. She didn't expand on it, but it matches ideas 11 and 16.

"we'll see what our failure modes are and systematically target those failure modes one at a time to see if we can resolve those failure modes by prompting"

— Margot van Laar
What to do with this

Keep a short log for each fix: failing case, cause, change and result.

11

Audit the patches you wrote for old models.

Newer models follow instructions more closely. A rule that once prevented errors can now be followed too strictly.
